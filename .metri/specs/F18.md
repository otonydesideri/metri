# F18 · Guardrails no CI do projeto

## Problema

Os guardrails do método só valem se rodarem também onde o Metri não está. Um merge feito à mão, fora da fila de integração, passaria sem nenhuma conferência, e o projeto deixaria de se sustentar sem o Metri.

## Solução

O CI do repositório do Metri roda lint, typecheck, testes e o `metri verify` a cada push e pull request, em Linux, numa máquina sem o app. Ele usa a mesma versão do método que o processo de construção usa, e os checks de fronteiras, datas, tokens e `SOURCE OF TRUTH` passam ou falham como no Workspace. Desde a slice de fundação, um lint de portabilidade segura o código que só rodaria no Linux.

## Casos de uso

- UC18.1 · Rodar os guardrails no CI

## Decisões de implementação

- GitHub Actions em `ubuntu-latest`, com o Node da raiz (24) e o pnpm do `packageManager`: instalação travada pelo lockfile, lint, typecheck, testes, `pnpm verify` e o e2e com Playwright, sem nenhum segredo da Anthropic. T3 Code, Orca e Superset usam GitHub Actions (`pingdotgg/t3code@a4c9494b:.github/workflows/ci.yml:22`; `stablyai/orca@e3639ef8:.github/workflows/pr.yml:802`; `superset-sh/superset@44d2a8ad:.github/workflows/ci.yml:136-137`).
- Um job diário no Node 26, que vira LTS em 28/10/2026, como o Orca (`stablyai/orca@e3639ef8:.github/workflows/node-next-compat.yml:1-7`).
- A versão do método é a que a raiz instala: a tag até o tracer, o link do workspace depois (T14.1).

## Decisões de teste

- O próprio workflow, num pull request; o lint de portabilidade tem os testes no método (T0.4).

## Fora de escopo

- O workflow de CI que o `metri init` entrega aos projetos novos (F21).

## Notas

- Abordagem descartada: o workflow de CI para projetos novos já no primeiro marco. O único projeto é o próprio Metri.
- Os jobs de macOS (F28) e de Windows (F25) entram no `beta` (ADR-0010).
- Abordagem descartada: sem CI no primeiro marco, confiando na fila de integração. Um merge feito à mão não teria guarda nenhuma.
