# F10 · Runs e eventos

## Problema

Um agente trabalhando é uma caixa-preta: o humano não vê o que ele faz, não sabe se parou há uma hora e perde o fio quando o servidor reinicia. Para aprovar uma tela, o humano precisa ver o app rodando, sem misturar com o checkout em que ele mesmo trabalha.

## Solução

A tela do Run mostra a conversa ao vivo, montada dos eventos que o Metri grava antes de mostrar. Se o servidor reinicia, o Run é retomado pela sessão do harness ou fica falho com aviso. Os subagentes aparecem dentro da conversa do Run que os disparou, e o custo de cada Run é uma estimativa feita pelo Metri. Um Run sem evento por muito tempo, ou repetindo a mesma chamada, gera um aviso na Inbox, e o estado dele não muda sozinho. O humano manda mensagem a um Run, interrompe o turno ou o cancela. A lista de Runs mostra todos, com filtros. Antes de cada migration, o Metri copia o banco e confere a cópia, e um comando restaura uma cópia com o servidor parado. O Preview sobe o app do Workspace de um Run ou, para a branch da slice em aceite e a branch padrão, num Workspace próprio, e o mostra em desktop e mobile.

## Casos de uso

- UC10.1 · Acompanhar um Run
- UC10.2 · Ver o app rodando
- UC10.3 · Restaurar o banco a partir da cópia de uma migration
- UC10.4 · Conduzir um Run
- UC10.5 · Retomar um Run depois de reiniciar
- UC10.6 · Ser avisado de um Run travado
- UC10.7 · Ver a lista de Runs

## Decisões de implementação

- O registro de eventos segue o ADR-0016: a tabela que só cresce, com a sequência global e a por Run; as projeções `runs` e `run_items` gravadas na mesma transação; os deltas de streaming só pelo WebSocket; o evento bruto do harness em NDJSON por Run, na pasta de dados; e a época do banco, trocada na restauração. O tempo real segue o ADR-0013.

| Estado do Run (BR74) | Entra quando |
| --- | --- |
| na fila | o Run é criado enquanto outro Run usa o mesmo Workspace |
| preparando | o Workspace é preparado e a sessão do harness abre |
| rodando | a sessão está num turno |
| esperando você | uma aprovação, uma pergunta ou um portão espera o humano, ou o humano interrompeu o turno |
| verificando | o `report` chegou, o turno ficou ocioso, e os checks rodam |
| concluído | o papel entregou: Goal atingido (e portão aprovado, quando há) ou proposta de padrão |
| falhou | três correções no mesmo check, setup falho, sem `report` depois de dois lembretes, retomada falha ou erro do harness |
| sem orçamento | o orçamento do Run acabou |
| interrompido | a partida encontrou o Run ativo; a retomada vem em seguida |
| cancelado | o humano cancelou, ou recusou o portão que o Run esperava |

- Cada Run grava o motivo de parada junto do estado final, a versão do método com que rodou (T14.1) e o Run de onde veio.
- O aviso de Run travado (UC10.6) é um timer no processo, que olha a cada minuto o último evento de cada Run rodando (ADR-0005).
- O custo (BR61) soma tokens de entrada, de saída e de cache pela tabela de preços do driver, com a data e a fonte de cada preço.
- A partida segue esta ordem: trava da instância única, cópia e migrations (UC10.3), limpeza dos processos órfãos (ADR-0017), Runs ativos marcados como interrompidos, retomadas (UC10.5) e só então o Scheduler.
- A cópia de migration (UC10.3) usa `VACUUM INTO` e `PRAGMA quick_check` e fica na pasta de dados; a restauração é um comando do app-api que recusa rodar com a instância viva, como no T3 Code (`pingdotgg/t3code@4dbc0129:apps/server/src/serviceLauncher.ts:66-73,109-177`).
- O Preview (UC10.2) roda o run dos scripts do projeto com a `METRI_PORT` do Workspace. Antes de mostrar no quadro, o servidor confere os cabeçalhos `X-Frame-Options` e `frame-ancestors` da resposta do app. O quadro usa `sandbox="allow-scripts allow-same-origin allow-forms allow-popups"` e `referrerpolicy="no-referrer"`, como o Vibe Kanban (`BloopAI/vibe-kanban@d5cbb538:packages/ui/src/components/PreviewBrowser.tsx:32-33,504-511`).

## Decisões de teste

- O registro de eventos: anexar e projetar no SQLite de e2e, com a falha da projeção desfazendo o evento. O WebSocket: assinatura, reconexão e `reset`. O Run: abrir, conduzir, retomar e travar com o driver falso. A perda zero: um e2e que derruba o processo do servidor no meio de um Run.

## Notas

- Abordagem descartada: sem o aviso de Run travado e sem os Previews da branch padrão e da slice. No primeiro marco, o humano deixa o Metri rodando e sai, e é vendo a slice rodando que ele a aprova.
- Abordagem descartada: o mapa de Runs já no primeiro marco. Com um ticket por vez no projeto, o mapa vira uma linha reta; como cada Run grava o pai, ele entra na F13 sem retrabalho.
- Abordagem descartada: OpenTelemetry no servidor local. Nenhuma ferramenta do mercado usa OTel como fonte das telas, e OpenCode, Kilo Code e T3 Code só exportam por OTLP com um endpoint configurado. O registro de eventos é a fonte das telas, e o log do servidor é o do método. Um arquivo de log com rotação entra no `beta`, com a casca desktop, pelo log estruturado sob demanda. O Metri não liga o OpenTelemetry dos harnesses.
- Abordagem descartada: a conversa só no histórico do harness. Contraria o princípio de experiência "Agente é função", que monta a conversa dos eventos.
