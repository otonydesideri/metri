# F10 · Runs e eventos

## Problema

Um agente trabalhando é uma caixa-preta: o humano não vê o que ele faz, não sabe se parou há uma hora e perde o fio quando o servidor reinicia. Para aprovar uma tela, o humano precisa ver o app rodando, sem misturar com o checkout em que ele mesmo trabalha.

## Solução

A tela do Run mostra a conversa ao vivo, montada dos eventos que o Metri grava antes de mostrar. Se o servidor reinicia, o Run é retomado pela sessão do harness ou fica falho com aviso. Os subagentes aparecem dentro da conversa do Run que os disparou, e o custo de cada Run é uma estimativa feita pelo Metri. Um Run sem evento por muito tempo, ou repetindo a mesma chamada, gera um aviso na Inbox, e o estado dele não muda sozinho. A lista de Runs mostra todos, com filtros. O Preview sobe o app do Workspace, da branch da slice em aceite ou da branch padrão, sempre num Workspace próprio, e o mostra em desktop e mobile.

## Notas

- Abordagem descartada: sem o aviso de Run travado e sem os Previews da branch padrão e da slice. No primeiro marco, o humano deixa o Metri rodando e sai, e é vendo a slice rodando que ele a aprova.
- Abordagem descartada: o mapa de Runs já no primeiro marco. Com um ticket por vez no projeto, o mapa vira uma linha reta; como cada Run grava o pai, ele entra na F13 sem retrabalho.
- Abordagem descartada: a conversa só no histórico do harness. Contraria o princípio de experiência "Agente é função", que monta a conversa dos eventos.
