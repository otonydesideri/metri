# F2 · Harness Claude Code e papéis

## Problema

O Metri não tem loop de agente próprio. Ele precisa do Claude Code pronto na máquina, com o login que a pessoa já fez, e precisa saber que modelo cada papel usa. Uma chave de API esquecida no ambiente da máquina desvia a cobrança do plano da conta Claude para a API sem ninguém perceber.

## Solução

Na tela de Harnesses, o humano vê se o Claude Code está pronto: o binário em uso (o que vem com o Agent SDK ou outro caminho configurado), a versão e o resultado do último teste, que abre uma sessão curta do harness. O Metri avisa quando a versão difere da suportada. A pessoa escolhe o modo, conta Claude ou API, e o modo decide se a chave de API do ambiente chega ao Run; a tela mostra a origem da credencial que o SDK informa. Quem prefere a chave de API entra com ela no próprio Claude Code. Na configuração do projeto, o humano escolhe o modelo de cada papel, e na tela do ticket pode trocar o modelo antes de despachar.

## Casos de uso

- UC2.1 · Conferir o Claude Code
- UC2.2 · Escolher o modelo de cada papel e de cada ticket
- UC2.3 · Usar o Claude Code com chave de API

## Decisões de implementação

- O pacote dos drivers, pelo contrato da S2 e pelo ADR-0015: o contrato sem fornecedor, o driver do Claude e o driver falso. Só um arquivo do driver do Claude carrega o SDK em tempo de execução; o resto o usa só como tipo. O servidor local roda o driver no próprio processo.
- O SDK fica com versão exata, e o binário padrão é o que vem com ele; outro caminho é configurável, com a versão conferida por `--version` contra a faixa suportada, como no Superset e no T3 Code.
- `check()` abre uma sessão curta, com um turno só, e devolve versão, modelo e a origem da credencial que o SDK informa (`apiKeySource` e `accountInfo`); nunca lê arquivo de credencial (BR4).
- O modo do harness (UC2.3) mora na configuração do Metri, na pasta de dados, e vale para todos os projetos. O ambiente do processo do harness é montado por lista: no modo conta Claude, sem `ANTHROPIC_API_KEY` e `ANTHROPIC_AUTH_TOKEN`; no modo API, com os dois (ADR-0009).
- O mascaramento da BR103 é um filtro único, aplicado antes de gravar evento, log ou saída de check, que troca os valores com os prefixos `sk-ant-` da Anthropic por `[redigido]`, como o GitHub Actions faz com os segredos (ADR-0009).
- O modelo de cada papel (UC2.2) fica na configuração do projeto; sem escolha, vale o padrão do harness. A troca por ticket vale até o próximo Run dele e não muda o plano (BR24).

## Decisões de teste

- Três camadas (ADR-0004, Consequências): a transcrição gravada, que roda o driver de verdade e troca só a chamada ao SDK, como no T3 Code; o CLI falso apontado como binário, que grava os argumentos e o ambiente que recebe, como no Orca, e prova o modo conta Claude sem chave; e o teste ao vivo, com `METRI_LIVE_CLAUDE=1` e o login de quem roda. O CI roda só as duas primeiras.
- A tela de Harnesses: o e2e com o driver falso.

## Fora de escopo

- Guardar a chave de API no Metri: ela fica no próprio Claude Code.
- Codex (F19).
- Modelo escolhido pela complexidade do ticket (F20).

## Notas

- Abordagem descartada: a chave de API no cofre do sistema já no primeiro marco. Integrar o cofre de três sistemas operacionais, com módulo nativo, num marco em que a única pessoa que usa o Metri entra com a própria conta Claude.
- Abordagem descartada: sem tela, com o login detectado na partida e o modelo de cada papel na Definição de agente. A troca de modelo viraria commit.
- Os termos da Anthropic sobre o login da conta Claude pelo Agent SDK num produto de terceiros são ambíguos (ADR-0009). Por isso o caminho por chave de API também está no `now`, no UC2.3, que absorveu a antiga F23.
- Abordagem descartada: o Metri guardar a chave no cofre do sistema, com um arquivo de reserva onde não há cofre, como no WSL. O Metri passaria a carregar um segredo.
