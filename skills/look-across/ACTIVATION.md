# Activation

The Source decides how the system is built; the project decides what only it knows: whether it needs a capability, which provider it uses, who owns the data.

## Three classes of decision

| Class | What it is | In /look-across |
| --- | --- | --- |
| GLOBAL | A rule that holds in every project | Defined: applied as it is |
| GLOBAL_CONDITIONAL | A capability the project may not have; when it has it, its owner already decided the shape | Inferred from the UCs and BRs by its `activation` question, confirmed at the plan gate |
| PROJECT_SPECIFIC | A concrete value only the project knows: provider, owner entity, topology | Asked when a UC needs it |

- The stack is GLOBAL (`node_modules/metri/architecture/defaults/stack.md`): ask only when the product doesn't fit it, and a swap is an ADR.
- GLOBAL_CONDITIONAL without the need stays inactive, with nothing of it asked.
- An activated GLOBAL_CONDITIONAL capability follows the form its global owner writes (`node_modules/metri/skills/writing-for-agents/RULE-FORMAT.md`, "Forma escrita sem instância"); activation resolves only its PROJECT_SPECIFIC values.
- A PROJECT_SPECIFIC value is resolved before the first point of the project that depends on it, and never with a choice the Source did not declare as its default.

## Order

1. Identify the capabilities the `now` UCs and their BRs need.
2. Apply the GLOBAL.
3. Infer each GLOBAL_CONDITIONAL by its `activation` question.
4. Ask the PROJECT_SPECIFIC values a UC needs, each delegation only when its trigger shows up in a UC.
5. Record them in the Project Architecture and, when it applies, in an ADR.
6. Validate the activated architecture by the verification of each activated owner.

A trigger that shows up later, like the first job or the first asset, is resolved by the /look-across that plans it, by steps 3 to 6.

## Record

`.metri/ARCHITECTURE.md` (created by `metri init`) keeps the current state, one line per item under its section: what exists in the code and the decisions in force, each capability and delegation from the moment the plan activates it (`pnpm rules-for` reads them); the slices and tickets still to build are the MATRIX's.

- "Stack": only what differs from `node_modules/metri/architecture/defaults/stack.md`, with its ADR; a swapped default of a rule also gets its line in "Exceções e defaults trocados".
- "Caminho linear": the project's flow as numbered steps, each naming its owner as `` `arquivo:símbolo` `` and what it does in one line (`` 1. `apps/app-api/src/main.ts:bootstrap` sobe o Fastify com o prefixo `/api`. ``); /accept adds the owners of each slice it prunes. A step that deviates from `node_modules/metri/architecture/backend/layers.md`, "O caminho de uma request", ends with its ADR.
- "Capacidades ativas": one line per id of the "Capacidades condicionais" table of `node_modules/metri/architecture/INDEX.md` the project activated, with the values its rule's `not_covered` leaves to the project: `- <id>: <valores>` (`- <id>: —` when it leaves none).
- "Delegações": one line per resolved delegation of the matrix below, named by its Subject: `- <Assunto>: <valor escolhido>`.
- "Caminhos do projeto": one line per path that depends on a project decision, such as a package the project owns: `- <glob> → <rule id>` (`pnpm rules-for --help`); the section enters with its first line.
- "Exceções e defaults trocados": one line per deviation, naming the rule id it deviates from and ending with its ADR: `` - `<rule id>`, "<Seção>": <estado vigente> → ADR-NNNN ``; `pnpm rules-for` delivers the line as `exceção:` only with that rule. A project rule that replaces a global one: `- <rule id> substituída pela regra do projeto → ADR-NNNN`.
- "Áreas ativas": generated by `pnpm rules-index` below the marker; never written by hand.

The "ADR when" conditions apply to what this activation or a later trigger decides, not to what the project already had; an exception to a global rule or a swapped default always has its ADR. A resolved delegation that meets the "ADR when" condition of its row (the ADR criterion applied to it) or, for a conditional capability, the ADR criterion itself (`node_modules/metri/skills/domain-language/ADR-FORMAT.md`, "When to offer an ADR") gets an ADR (call the Skill tool with "domain-language"), which keeps the why; the ARCHITECTURE.md line keeps the current state and ends with the ADR id.

## Need without coverage

When a project need has no global rule, isn't declared PROJECT_SPECIFIC, contradicts an existing rule, needs a new exception or needs a structural mechanism no rule covers, activation stops and applies the escape rule of `AGENTS.md` ("How to work here"), naming the case ARCHITECTURE DECISION REQUIRED:

```text
stop → ARCHITECTURE DECISION REQUIRED → decide → update the Source (global rule) or record an ADR (exception or structural project decision) → update the Project Architecture → continue
```

## Delegation matrix

Every decision the Source delegates to the project has a row here, with nine fields. The decision of a conditional capability lives in its owner rule instead, listed in the "Capacidades condicionais" table of `node_modules/metri/architecture/INDEX.md`: its trigger is the `activation` key, and what the project decides is a `not_covered` entry with the target `project:ARCHITECTURE`. When an owner starts delegating a new decision, its row enters this matrix, or the owner rule of the conditional capability, in the same edit.

The Subject is the label of the line in "Delegações".

| Subject | Class | Trigger | Global owner | The project decides | Source constraints | Default | Record | ADR when |

## Examples

- A project that sends a confirmation e-mail, stores product photos and has no expensive read activates mail and storage and resolves vendor, provider and buckets; cache and observability raise no question, and bounded contexts stay at the default of one context.
- A command from one module over another is a need without coverage, because `backend/modules.md` delegates the integration beyond the shared contract to the project: activation stops at ARCHITECTURE DECISION REQUIRED.

## Check

- Did activation ask only what has a trigger in the project, and nothing about a GLOBAL decision?
- Does each activated GLOBAL_CONDITIONAL capability follow its owner, with only its PROJECT_SPECIFIC values resolved?
- Was every PROJECT_SPECIFIC value resolved before the first point that depends on it, with no default the Source didn't declare?
- Does `.metri/ARCHITECTURE.md` keep the activated capabilities and the chosen values?
- Does every delegation that meets its "ADR when" condition have an ADR?
- Did every need without coverage stop as ARCHITECTURE DECISION REQUIRED, with no improvised value, mechanism or exception?
- Does every decision the Source delegates to the project have a row in the matrix with its nine fields, or live in the owner rule of its conditional capability, in `activation` and `not_covered`?
