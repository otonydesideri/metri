# Activation

The Source decides how the system is built; the project decides what only it knows: whether it needs a capability, which provider it uses, who owns the data. This file is the contract between the two: what activation asks, when it asks, and where the answer lives.

## Three classes of decision

| Class | What it is | At activation |
| --- | --- | --- |
| GLOBAL | A rule that holds in every project | Applied, with no question |
| GLOBAL_CONDITIONAL | A capability the project may not have; when it has it, its owner already decided the shape | One question: does the project need it? |
| PROJECT_SPECIFIC | A concrete value only the project knows: provider, owner entity, package, topology | Resolved before the first point that depends on it |

- Never ask what the Source already decided: a GLOBAL decision is applied as it is.
- GLOBAL_CONDITIONAL: ask only whether the project needs it; without the need, it is not activated and nothing of it is asked.
- An activated GLOBAL_CONDITIONAL capability follows its global owner, by the transition rule (`.metri/skills/writing-for-agents/RULE-FORMAT.md`, "Regra de transição"); activation resolves only its PROJECT_SPECIFIC values.
- A PROJECT_SPECIFIC value is resolved before the first point of the project that depends on it, and never with a choice the Source did not declare as its default.

## Not a questionnaire

Each question hangs on the trigger of its delegation: with no trigger in the project, the question doesn't exist. Never walk the whole matrix as a fixed questionnaire: a question without a trigger forces a choice the project can't make well, and a choice made without need becomes a dependency nobody asked for.

## Order

1. Identify the project's capabilities.
2. Apply the GLOBAL.
3. Evaluate the GLOBAL_CONDITIONAL triggers.
4. Resolve the applicable PROJECT_SPECIFIC values.
5. Record them in the Project Architecture and, when it applies, in an ADR.
6. Validate the activated architecture by the verification of each activated owner.

A delegation whose trigger shows up after the initial activation, like the first job or the first asset, is resolved at that moment, by steps 3 to 6.

## Record

`docs/architecture/INDEX.md` (copied from `.metri/skills/setup/INDEX-TEMPLATE.md`) keeps the current state, and each `<...>` placeholder line is replaced by the project's lines or deleted when there are none:

- `source:` the tag checked out in `.metri/`, as `.metri@<tag>`.
- "Stack": only what differs from `.metri/architecture/defaults/stack.md`, with its ADR.
- "Caminho linear": only the deviations from `.metri/architecture/backend/layers.md`, "O caminho de uma request", with their ADRs.
- "Capacidades ativas": one line per id of the "Capacidades condicionais" table of `.metri/architecture/INDEX.md` the project activated, with the values its rule's `not_covered` leaves to the project: `- <id>: <valores>`.
- "Delegações": one line per resolved delegation of the matrix below, named by its Subject: `- <Assunto>: <valor escolhido>`.
- "Caminhos do projeto": one line per path that depends on a project decision, such as the package of the API contract: `- <glob> → <rule id>` (`pnpm rules-for --help`).
- "Exceções e defaults trocados": the ADR of each deviation.
- "Áreas ativas": generated by `pnpm rules-index` below the marker; never written by hand.

The "ADR when" conditions apply to what this activation or a later trigger decides, not to what the project already had; an exception to a global rule or a swapped default always has its ADR. A resolved delegation that meets the "ADR when" condition of its row (the ADR criterion applied to it) or, for a conditional capability, the ADR criterion itself gets an ADR (call the Skill tool with "domain-language"), which keeps the why; the INDEX line keeps the current state and ends with the ADR id.

## Need without coverage

When a project need has no global rule, isn't declared PROJECT_SPECIFIC, contradicts an existing rule, needs a new exception or needs a structural mechanism no rule covers, activation stops and applies the escape rule of `AGENTS.md` ("How to work here"), naming the case ARCHITECTURE DECISION REQUIRED:

```text
stop → ARCHITECTURE DECISION REQUIRED → decide → update the Source (global rule) or record an ADR (exception or structural project decision) → update the Project Architecture → continue
```

Activation never improvises a value, a mechanism or an exception.

## Delegation matrix

Every decision the Source delegates to the project has a row here, with nine fields. The decision of a conditional capability (the "Capacidades condicionais" table of `.metri/architecture/INDEX.md`) lives in its owner rule instead: its trigger is the `activation` key, and what the project decides is a `not_covered` entry with the target `project:architecture/INDEX`. When an owner starts delegating a new decision, its row enters this matrix, or the owner rule of the conditional capability, in the same edit.

The Subject is the label of the line in "Delegações".

## Examples

- A project that sends a confirmation e-mail, stores product photos and has no expensive read activates mail and storage and resolves vendor, provider and buckets; cache and observability raise no question, and bounded contexts stay at the default of one context.
- The first job shows up months after the initial activation: the queue delegation is resolved then, by steps 3 to 6 of "Order".
- Requiring workers in their own app is a need without coverage, because that design is open in `backend/async-jobs.md`: activation stops at ARCHITECTURE DECISION REQUIRED.

## Check

- Did activation ask only what has a trigger in the project, and nothing about a GLOBAL decision?
- Does each activated GLOBAL_CONDITIONAL capability follow its owner, with only its PROJECT_SPECIFIC values resolved?
- Was every PROJECT_SPECIFIC value resolved before the first point that depends on it, with no default the Source didn't declare?
- Does `docs/architecture/INDEX.md` keep the activated capabilities and the chosen values?
- Does every delegation that meets its "ADR when" condition have an ADR?
- Did every need without coverage stop as ARCHITECTURE DECISION REQUIRED, with no improvised value, mechanism or exception?
- Does every decision the Source delegates to the project have a row in the matrix with its nine fields, or live in the owner rule of its conditional capability, in `activation` and `not_covered`?
